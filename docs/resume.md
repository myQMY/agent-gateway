# 简历 bullet 与口径红线

**这是一套评测装置 / 运行时平台，非面向用户的 Agent 应用**：被测量、被改进的是
Agent 运行时与评测链路本身，任务集只是标尺，不是做一个对话产品，也不是能评测
任意外部 Agent 的通用平台。两个仓库独立、commit 历史独立，共用同一套方法论。

> 面向 **Agent 基建 / AI 后端 / 评测平台工程（A 类）** 岗位。本文件供用户本人抄写与自检，
> 不是项目说明；所有数字必须连边界一起讲。

## 0. 首句定位（必须原样保留）

上面第一段是简历首句，不能删、不能挪到文末。面试官若按「你做了个对话产品」或
「这套东西能评测任意外部 Agent」这类误读提问，后面所有解释都在逆风。

## 1. 一句话主线（口述用）

`agent-reliability-harness`（P1）做「运行时 + 评测可观测」，`agent-gateway`（P4）做
「运行时与模型供应商之间的服务化出口」；两者**互补而非续作**，P4 只**只读** P1 的
`mvp_10.jsonl` 作为回放负载，共同方法论是「配置即自变量 + 单变量对照 + 产物逐字节可复现
+ 边界写进文档」。

## 2. 项目一：agent-reliability-harness（评测装置 / 运行时平台）

> 纯 Python 标准库、零第三方依赖、零密钥即可全量复现；612 条 unittest 全绿 / 23 commits（2026-11-06 收口时）
> / 22 份报告 + 14 组按 `run_id` 归档（**相当比例是读归档与源码的守门测试，对外说 605 全绿
> 必须带此限定**）。

- **搭建可证伪的评测装置**：有状态业务任务 + 数据库终态自动判分 + `pass^k`（同一任务连续
  k 次全过）+ 全链路 trace 首个偏离点归因，把「一次运行时改动是否让 Agent 更稳」从 demo
  观感变成可复现对照（`python -m eval.run --tasks tasks/mvp_10.jsonl --k 3` 即可重跑）。
- **用单变量 A/B 逐项验证四条运行时护栏**（`schema_validation` / `idempotency` /
  `tool_retry` / `json_recovery`）：一组一条、一个 commit，2×8 全因子 + 30 seed 描述性统计
  （**不是显著性检验、不是 A/B 因果推断**）；`invalid_calls` 只是诊断量，论效果只看 `pass^k`。
- **做出「提升来自 harness 而非换模型」的可证伪对照**：fpm=60 时 `off` 0.1433 → 四护栏
  全开 0.3000（+0.1567），而把故障率降到 0 只到 0.2000（+0.0567），缺口 0.1000 →
  换模型最多兑现 36.2%（**fpm 只控四类输出级故障、非推理能力；fpm=0 不是天花板；
  0.10 来自 idempotency 修 T03 固有重复写；不外推真实模型**）。
- **把测量装置自身的缺陷做成工程故事**：W4 三轮真实模型两格 `pass^k` 均为 0.00，根因是
  判分的自由文本精确匹配；由此走完「发现装置缺陷 → 离线校准 → 修复重跑 → 分层结论」
  （**H1 未被检验（分母 0）而非被证伪；不是护栏在真实模型上有效**）；`pass^k` 分辨率
  恒为 1/N、与 k 无关，`mvp_30` 把它从 0.10 压到 0.0333、信息位点 3→19（**跨任务集只谈
  分辨率、scripted 基线不可相减**）。

## 3. 项目二：agent-gateway（Agent 网关 / LLM 中间件）

> 独立新仓库，核心纯标准库，FastAPI 只做 HTTP 适配；254 条 unittest 全绿（2026-11-09
> 口径修正后；**裸标准库下 14 个 HTTP 测试 skip，隔离 venv 全跑**）；按阶段单 commit
> 收口、工作区干净。仓库元数据（commit 数 / tracked 数）随提交增长，对外不写死。
> 两组 W1 归档三件逐字节可复现，`GatewayConfig` 零字段新增。

- **做深四条网关决策链路**：模型路由 + fallback、规范化请求的精确缓存（LRU/TTL）、
  固定窗口限流、幂等键重放；每条链路都有可测决策点与可归档 span，串行 off/on 单变量
  对照给出缓存命中 / 幂等 / 限流 / 降级四类事件计数与相对成本差（**成本差 0.1185 /
  0.1822 只在该合成回放 + 固定价格表内成立；全 fake 上游、零 API 成本、命中率由
  `repeat_rate` 决定；不外推生产、不宣称省钱**）。
- **把并发做成可验证的不变量而非性能数字**：有界容量闸门 + 线程池 + 同幂等键
  single-flight；32 个并发同 key → 上游恰好 1 次且台账 32 条不丢，40 并发 @
  `rpm_limit=3` → 200 恰 3 / 429 恰 37（**这些是并发不变量，不是 QPS、不是 SLA、不外推
  生产吞吐；那 1 次由幂等表 + 精确缓存共同保证，不是 single-flight 单独功劳**）。
  并发路径与串行 off/on 基准**互不相交**：不产 `cache_hit_rate` / `cost_saving` /
  `p95_ms`，不与 W1 归档相减或拼曲线。
- **补齐服务化与可复现工具链**：完整 SSE（role 首帧 / `usage` 尾帧 / `[DONE]` /
  `event: error` / `event: cancelled`）、参数化负载生成器、只读归档的确定性静态 trace
  视图（零 JS / 零外链、同归档逐字节相同）、可选容器清单（**Docker 是可选便利不是复现
  前提；本机无 Docker，build / compose 未实跑，只有静态清单与守门测试**）。
- **真实链路 W4 两格已执行一次且边界写死**（2026-11-09，本人执行，产生真实 API 成本）：
  off 直连 / on 经网关各 30 trial、run_id 不同，产出 P1 侧真实 token 与端到端延迟；
  两格 `pass^k` 均 0.00 是 P1 判分器收口红线的预期结果，**未产出 `pass^k` 正向结论、
  未验证网关收益**；两格自变量不同，不相减、不拼曲线、不宣称省钱。网关 `/metrics`
  决策计数那次未留档（脚手架缺陷，已修）。

## 4. 工程方法与两个实测真缺陷（面试主动讲）

- **方法**：配置即自变量、`config_hash` 只锁配置不锁代码（完整复现 = 同配置 + 同一 commit）、
  归档三件随仓库入库、守门测试把红线钉死在源码与文档上。
- **W2 真缺陷**：初版用「常驻 worker 循环 + 自建队列」，executor 关闭哨兵无人消费，
  `_python_exit` 的 `join()` 永久挂住、进程退出不了；用 `faulthandler` 定位后改成
  「容量闸门 + 每请求一个短任务」。
- **W3 真缺陷**：初版 single-flight 自检 `single_flight_waited` 恒为 0（fake 上游瞬时，
  leader 先完成），所谓并发自检退化成串行回放；改为 `BlockingUpstream` 阻塞首个上游调用
  直到全部提交，才真正打开并发窗口。
- 两处都写进了设计文档，不是「跑通了就收工」。

## 5. 岗位匹配与缺口（如实讲）

- **主投 A 类**：Agent 基建 / AI 后端 / 评测平台工程；次投 Agent 评测 / 归因。
  **不投算法研究 / RL 后训练**（两个项目零训练）。
- 出勤：每周 5 天，满足 JD 常见的「每周 4–5 天、连续 3–6 个月」门槛。
- **缺口如实讲，不靠改项目补**（停止线）：分布式并发、Docker/K8s 沙箱实跑、服务化 API
  的生产化、Redis/MQ、LLM-as-a-Judge、生产 Benchmark；靠讲清取舍 + 面试前补概念。
- 「互联网」是公司类型不是岗位方向，与 A 类正交；放宽到通用业务后端岗也可投，靠
  W2/W3 的并发 / 队列 / 容器化证据补信号。

被追问时统一答法（详见 [interview.md](interview.md)）：

1. 先给边界，再给数字：「这是合成回放内的相对量，不是上线后的收益」；
2. 主动说出未验证项，不等着被拆穿：「网关 W4 两格已执行一次但未产收益结论、网关 /metrics 那次未留档、Docker 未实跑、判分器是收口红线」；
3. 讲清取舍而不是辩解：「不做分布式并发是 R6 要求单机一键复现，不是不会做」；
4. 不硬凑正向通过率：`pass^k` 0.00 就讲装置缺陷与校准过程，不包装成成功。
