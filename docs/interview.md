# 面试追问预案

> 配套 [resume.md](resume.md)。每题三段式：**可直接说的话** → **依据文件** → **不许越界的话**。
> 通用原则：先给边界再给数字；主动说未验证项；讲取舍不辩解；不硬凑正向通过率。
> 岗位方向固定为 **A 类：Agent 基建 / AI 后端 / 评测平台工程**。

## A 组：定位（最容易被误读，答错后面全逆风）

### A1. 「你这是做了一个 Agent 吗？能演示一下对话吗？」

> 这是一套**评测装置 / 运行时平台，非面向用户的 Agent 应用**。被测量、被改进的是
> harness 本身，任务集只是标尺。P1 里确实有一个多轮工具调用循环和六个固定工具，但它是
> 被测对象、不是产品；P4 是运行时到模型供应商之间的服务化出口，连对话界面都没有。
> 想看「能跑的东西」，我可以跑一条有状态任务，给你看数据库终态判分和全链路 trace。

**依据**：P1 `README.md` 首屏、`docs/mvp-design.md`；P4 `README.md`「是什么」。
- ❌ 说成「做了一个智能客服 / 面向用户的 Agent 产品」。

### A2. 「那它能评测任意 Agent 吗？我把我的 Agent 接进来能打分吗？」

> **不能，它不是通用 Agent 评测平台**。接口有三堵墙：`Backend` 只有
> `generate(messages)->ModelReply` 三种实现、没有插件机制；工具调用循环归 harness 自己；
> 协议绑死单轮单 JSON + `final` 终止、六个固定工具、只有 `mvp_10` / `mvp_30` 两套任务且
> 任务自带 `target_db`。可插拔的是**动作生成策略**，不是任意 Agent。P4 同理，只实现
> OpenAI 兼容 `chat/completions` 的一个子集，不接任意外部 Agent。

**依据**：P1 `README.md` §边界、`docs/tech-stack.md`；P4 `docs/design.md` §0「不是什么」。
- ❌ 「支持接入任意 Agent 并统一治理」。

### A3. 「两个项目什么关系？是不是同一个东西的 v1 / v2？」

> **互补、不是续作**。P1 是「运行时 + 评测可观测」，P4 是「运行时与供应商之间的服务化
> 出口」，两个独立仓库、独立 commit 历史。P4 只**只读** P1 的 `tasks/mvp_10.jsonl`
> 把脚本动作转成请求流做回放负载，不 import P1 代码、不写 P1 目录、更不是运行时直连
> （直连是网关 W4，两格已执行一次、未产收益结论）。共用的是方法论：配置即自变量、单变量对照、逐字节可复现。

**依据**：P4 `docs/design.md` §0「与 P1 的关系」、`bridge/README.md`。
- ❌ 「两个项目合并成一个通用 Agent 评测平台」「在 P1 基础上迭代出的第二版」。

## B 组：架构

### B1. 「为什么核心全用标准库？FastAPI 只在一层？」

> 为了让**复现不依赖环境**。P1 的差异化就是「clone 下来 `python -m unittest` 全绿、
> 归档逐字节可复现」，P4 沿用这条纪律：路由 / 缓存 / 限流 / 幂等 / 成本核算都能在裸
> Python 下单测，FastAPI 只在 `app.py` 做 HTTP 适配，`requirements.txt` 只有 3 个包。
> 代价是 SSE 只支持 `chat/completions` 子集、没有 tool_calls 增量，我如实标注了。

**依据**：P4 `docs/design.md` §0/§3；`tests/test_project_contract.py`（守门测试钉死核心零依赖）。

### B2. 「网关能力为什么只做四个？」

> 参考 LiteLLM / Portkey / Cloudflare AI Gateway 的能力边界，**选 4 个做深、不做全**：
> 路由 + fallback、精确缓存、固定窗口限流、幂等键。每个都有一个可测决策点和一个可观测
> 输出。明确不做延迟感知路由、语义缓存、令牌桶、跨实例锁 —— 因为要保住「单机一键
> 复现」这条 R6，也因为做浅了反而讲不出东西。成本核算与 span 是横切能力。

**依据**：P4 `docs/design.md` §2、§7。

### B3. 「并发怎么做的？为什么不上 Redis / MQ / K8s？」

> 单进程内有界容量闸门 + 线程池 + 同幂等键 single-flight，四个共享组件各带 `RLock`，
> 上游 I/O 放在锁外让它真并行。不上分布式组件是 R6 的硬约束：一旦引入 Redis/K8s，
> 「单机一键复现」就没了，而这是两个项目共同的差异化。**这是取舍，不是能力缺失**；
> 分布式限流、跨实例缓存我写在边界里，面试前补了概念。

**依据**：P4 `docs/design-w2.md` §1、「两条互不相交路径」；`gateway/concurrency.py`。
- ❌ 「已容器化部署 / K8s 就绪」。

## C 组：数字（最容易被拆穿）

### C1. 「0.1433 → 0.3000，是不是说明护栏让 Agent 成功率翻倍？」

> 这是 **fpm=60 的合成故障注入下的对照**：`off` 0.1433 → 四护栏全开 0.3000
> （+0.1567）；把故障率降到 0 只到 0.2000（+0.0567），缺口 0.1000，所以换模型最多
> 兑现 36.2%。四个边界必须一起讲：fpm 只控四类输出级故障、不是推理能力；`fpm=0`
> 不是天花板；那 0.10 主要来自 idempotency 修掉 T03 的固有重复写；实验是 **2×8 全因子
> + 30 seed 描述性统计，不是 A/B、不作因果解读、不外推真实模型**。

**依据**：P1 `experiments/w3_attribution.md`、`experiments/w3_guard_matrix.md`。
- ❌ 「护栏显著提升真实模型通过率」「W3 被完整验证」。

### C2. 「真实模型两格都是 0.00，那项目不是失败了吗？」

> 不是「护栏无效」的证据，是**装置缺陷的证据**。首轮 0 个探针拒绝，H1 **未被检验
> （分母 0），不是被证伪**；三层根因里最关键的是判分器：`grader.py` 做结构化
> `state != target` diff，但 `target_db` 夹带 `audit_log.notify.message` 自由文本，
> 效果上退化成字面精确匹配。W4-b 给 openai 后端接同源输出故障注入，W4-c 把被替换的
> 干净动作写进**只读 side-car、绝不回灌模型**，15/15 配回、两格仍 0.00。
> 我拿到的结论是「发现装置缺陷 → 离线校准 → 修复重跑 → 分层结论」这条工程链，
> **不是护栏在真实模型上有效**。改判分器是收口红线，所以我没有为了好看的数字去动它。

**依据**：P1 `experiments/w4_report.md` / `w4b_report.md` / `w4c_report.md`、`docs/w4-design.md`。
- ❌ 「W4 验证通过」「跑完 W4 就能得到正向 pass^k 结论」。

### C3. 「成本差 0.1185 / 0.1822 是不是说明能省钱？」

> **不能这么说**。这是两组合成回放（一组合成日志、一组 P1 任务集）在固定价格表下的
> 相对量，全 fake 上游、零 API 成本、零网络调用；命中率主要由 `repeat_rate` 决定，
> 它是**自变量不是优化成果**。它只证明「缓存命中不计费」「降级用更贵模型」两条机制
> 在跑且可测，**不外推生产、不宣称省钱**。网关 W4 挂真实供应商的两格已执行一次，
> 但未产出收益结论；两格自变量不同，不能与本表的合成回放数字相减或拼曲线。

**依据**：P4 `docs/design.md` §5、`experiments/runs/*/report.md`。
- ❌ 「成本下降 XX%，上线后能省钱」「显著提升真实成本」。

### C4. 「p95 是多少？QPS 能到多少？」

> 报告里的 `p95_ms` 是 **SHA256 派生的确定性模拟延迟**，不是网络延迟、不是生产 SLA，
> 报告不记录墙钟耗时。并发自检只给计数不变量（上游恰好 1 次、200/429 恰好几个），
> **不测 QPS、p95、墙钟**。这是刻意的：这些依赖机器和线程调度，写进报告就变成
> 无法复现的数字。真实端到端延迟在网关 W4 的 P1 结果行与 trace 里（`perf_counter`
> 量得），但那次网关 `/metrics` 决策计数未留档，且两格不相减。

**依据**：P4 `docs/design-w3.md` §2、`docs/design.md` R4/R5。
- ❌ 「真实 p95 = XX ms」「压测 QPS = XX」。

### C5. 「网关 W4 两格都跑过了，到底跑出了什么？」

> **两格已执行一次**（2026-11-09，本人执行，真实 API 成本），注意这是 **P4 的网关 W4**，
> 与 C2 里 P1 内部那轮 W4 校准实验不是同一件事。off 直连 / on 经网关各 30 trial，
> run_id 不同，产物完整；两格 `pass^k` 均 0.00 是判分器收口红线的预期结果，
> **不是网关有效或无效的证据**。拿到的是 P1 侧真实 token、端到端延迟与全链路 trace，
> 以及「缓存 / 幂等在真实请求流里确实触发」这一可观测事实（on 格 25/30 trial
> 延迟 < 100 ms）；**未产出 `pass^k` 正向结论、未验证网关收益**，网关 `/metrics`
> 决策计数那次未留档（脚手架缺陷，已修）。缓存改变模型输出序列，这格不是正常评测：
> **不相减、不拼曲线、不宣称省钱、不作因果解读**。

**依据**：P4 `w4/README.md`「本次执行结果」、`w4/out/`（本地产物未入库）、`docs/design-w4-tooling.md`。
- ❌ 「W4 已完成并得到正向结论」「在真实模型上验证了网关收益」。

## D 组：边界与测量口径

### D1. 「四条护栏还有 7 个任务恒失败，为什么不修完？」

> 四护栏已经达到**当前任务集的上限**：30/30 seed 下结果与「关故障 + 全开」相等，
> 剩下 7 个是脚本固有缺陷，与四类输出级故障无关。护栏的职责边界是修输出级故障，
> 越界去修脚本缺陷等于改标尺。要动就得动判分器或任务集，那是收口红线。

**依据**：P1 `experiments/w3_ceiling.md`、`experiments/w3_robustness.md`。

### D2. 「W3 和 W4 的数字能放一张图里看趋势吗？」

> **不能拼曲线**。四组自变量不同：故障注入率、后端类型、任务集、注入机制都不一样，
> 而且 `pass^k` 的**分辨率恒为 1/N、与 k 无关**（归档里「提高 k 提高分辨率」的说法
> 是错的，只在活文档纠正、不回溯改归档）。`mvp_30` 把步进从 0.10 压到 0.0333、
> 信息位点 3→19，那是**分辨率**的改进；跨任务集只谈分辨率，scripted 基线不可相减。

**依据**：P1 `experiments/w3_resolution.md`、`README.md` 三条边界。
- ❌ 「W3 与 W4 数字拼成一条曲线，说明持续改进」。

### D3. 「并发下的命中率 / 成本能不能和 W1 归档相减？」

> 不能。并发下「谁先命中缓存」由线程调度决定，成本和命中数字不可复现，所以我把
> **串行 off/on 基准**和**并发执行**定成两条互不相交的路径：并发路径不产
> `cache_hit_rate` / `cost_saving` / `p95_ms`、不写 `decisions.jsonl`、不与 W1 数字
> 相减。验收证据是 `GatewayEngine.handle()` 一行未改、`GatewayConfig` 零字段新增，
> 两组 W1 归档三件逐字节不变。

**依据**：P4 `docs/design-w2.md` §1、`tests/test_project_contract.py::test_w1_synthetic_archive_reproduces_byte_for_byte`。

### D4. 「Docker 那块实测过吗？」

> **没有，如实说**。本机没有 docker 命令，`docker build` / `compose up` 未实跑，
> 只交付了静态清单和守门测试。而且容器本来就是**可选便利、不是复现前提**：主路径
> 是裸 Python 全量测试 + 归档复验，`verify` 服务跑的正是同一套离线命令。

**依据**：P4 `docs/design-w3.md` §1、`Dockerfile` / `docker-compose.yml`。
- ❌ 「Docker 已实跑」「已容器化部署 / 生产可用」。

## E 组：工程缺陷（主动讲，加分项）

### E1. 「过程中踩过什么真实的坑？」

> 两个。W2 初版用「常驻 worker 循环 + 自建队列」，测试输出 `OK` 但进程退出时挂死；
> 用 `faulthandler` 定位到 4 个 worker 卡在 `queue.get` —— `concurrent.futures` 退出时
> 投进 executor 内部队列的关闭哨兵没人消费，`_python_exit` 的 `join()` 永久阻塞。
> 改成「容量闸门 + 每请求一个短任务」后干净退出。W3 初版 single-flight 自检
> `waited=0`，因为 fake 上游瞬时、leader 在其它请求到达前就完成，所谓并发自检退化成
> 串行回放；加 `BlockingUpstream` 阻塞首个上游调用才真正打开并发窗口。

**依据**：P4 `docs/design-w2.md` §2、`docs/design-w3.md` §2。

### E2. 「『上游恰好 1 次』是 single-flight 的功劳吗？」

> **不是单独功劳，这点我特意在文档里写明**。waiter 等 leader 完成后重走
> `engine.handle`，由**幂等表 + 精确缓存**共同挡住重复调用；single-flight 只是让等待
> 分支真的发生。另外 `queue_rejected` / `waited` 依赖调度，**只输出、不断言**；
> 背压用不提交线程的纯闸门场景验证，才能保证确定性。

**依据**：P4 `docs/design-w3.md` §2「口径诚实性」。

### E3. 「怎么保证『可复现』不是口号？」

> 三层：`config_hash = sha256(json(核心配置, sort_keys))[:12]` 只锁配置、不锁代码，
> 完整复现条件是「同配置 + 同一 git commit」；归档三件随仓库入库，clone 即可复验；
> 守门测试把红线钉死在源码和文档上（比如同归档渲染 HTML 逐字节相同、并发模块不得写
> 归档、核心模块不许 import 第三方包）。P1 同理，`run_id` 由配置派生、两个任务集的
> sha256 被测试钉死。

**依据**：P4 `docs/design.md` §4、`tests/test_project_contract.py`；P1 `AGENTS.md`。

## F 组：缺口与停止线（不辩解，讲取舍）

**依据**：P4 `docs/design.md` §7、P1 收口决定。

### F2. 「没有收益结论，怎么证明网关不是空转的中间件？」

> 四条决策链路各自产生可测事件，归档三件逐字节可复验。第二层是真实链路：2026-11-09
> 本人已把 off 直连 / on 经网关**两格各执行一次**（产生真实 API 成本），拿到 P1 侧真实
> token、端到端延迟与全链路 trace，以及「缓存 / 幂等在真实请求流里确实触发」这一可观测
> 事实；但 P1 判分器是收口红线不改，两格 `pass^k` 均 0.00 是预期结果，**未产出 `pass^k`
> 正向结论、未验证网关收益**，两格自变量不同，不相减、不拼曲线、不宣称省钱。我不会把
> 没验证的事写成验证了。

**依据**：P4 `docs/design.md` §0、§6；`w4/README.md`「本次执行结果」；`bridge/README.md`。
- ❌ 「W4 已完成」。
